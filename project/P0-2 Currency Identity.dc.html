TRAVEL PLANNER · P0-2 · DESIGN FOR REVIEW
Currency inference & currency identity
The guess becomes visible before Create, the failure is told where it happened, and an unset currency stops rendering as yen. Every frame 390 × 844, light only, built from existing app.css parts — no new component. Canonical spec: docs/design/p0-2-currency-design.md; every piece of copy here is from its §9, and everything else on these frames is sample trip data.
THE GUESS IS AMBER
A silent correct guess and a silent wrong guess are the same screen. Amber is the app's word for uncertain and yours, so the currency line is amber even when it worked.
TOLD WHERE IT HAPPENED
The lookup runs on the city field, so success and failure are on screen before Create. No string is the only account of a failure on a screen nobody opens.
SYMBOL + CODE + PLACE
$ is USD, ARS and MXN. ¥ is JPY and CNY. A provenance line always carries all three, so the inference is checkable.
CREATE IS NEVER GATED
A trip with no currency is a working trip with unpriced numbers. Nothing about money stops a trip existing.

THE ¥ DEFECT
Every money consumer reads currencySymbol || '¥', so an unset currency prices the whole trip in the demo trip's yen. An unset rate converts at 1:1.
THE BROKEN REMEDY

OPEN DECISION · C-1
Bare numbers, or no money at all until a currency is set? Recommendation: bare numbers. A number with no symbol is still true, and hiding the shopping estimates punishes the user for a failed lookup. The alternative is only defensible if unlabelled money is considered worse than absent money — a product-policy call, so it is yours.
