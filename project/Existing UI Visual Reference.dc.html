TRAVEL PLANNER · EXISTING UI · VISUAL BASELINE
What the current app actually looks like
Re-captured from the current web/ build at main — the same bundle Firebase Hosting serves at travel-planner-3e0d3.web.app. Nothing here is redesigned, re-spaced or re-coloured: every screen is a screenshot, and every specimen in the pattern boards is drawn with the literal values in web/css/app.css. Screens that cannot be reached in a running session are marked SOURCE-ONLY and left un-drawn on purpose.
Baseline refresh, 4 Sep 2026. The app gained real accounts since the first pass: anonymous sign-in is gone, replaced by Google or an emailed link, an account row now sits above the trips list, and sharing is a real Firestore envelope per link code. Every frame below was re-captured against that build; two screens are new to this reference (02 sign-in, 20 join — expired link).

02 · SCREEN GALLERY — VERIFIED
20 screens, as they render today
Every screen is presented in the same 390 × 844 mobile design frame, at 1:1 pixels and identical scale — the standard reference viewport for this document. The UI itself is untouched: the app was rendered at 390px wide with its real 16px page padding, real type sizes, real card and sheet geometry, and the 78px tab bar inside the 844px viewport. 06 · HOW TO USE THIS
If you build a new screen tomorrow
Start by copying a screen of the same shape
List → shop.js · push/detail → spend.js · map+sheet → map.js · form → note.js or the `.form` in parts.js. The shell (`.screen` → `.head` → one `.scroll`) is not negotiable.
Reuse parts.js before writing anything
backHeader, dayPills, tripChip/syncDot, checkbox, weatherBanner, emptyDay, swipeToDelete, bindDragReorder, draggableSheet, undoBar, the three modal editors — and now signInPanel/mountSignIn for anything that needs an account.
Keep the colour meanings
Only `:root` tokens, and only in their existing roles. A new hue would break the one thing the whole app teaches: given vs yours.
Never demand an account
Sign-in is offered in exactly two places (the account row and after accepting an invite) and always states what it buys. Everything else works signed out, on this phone.
Destruction is swipe → in-row confirm → undo
Never add a centred confirmation dialog. The only blocking interactions in the app are creating a trip and signing in.
Write copy like the app does
Plain sentences, second person, state the consequence, no marketing voice, no exclamation marks. Every warning names the tap that fixes it.
No new framework, no build step
One file in `web/js/screens/`, one `register()` line in app.js, and — only if unavoidable — a new block at the end of app.css. Existing inconsistencies stay as they are unless approved.
This board is a baseline record, not a design system to build from generically. Where a value here disagrees with `web/css/app.css`, the stylesheet wins. Frames re-captured 4 Sep 2026 against `main`; if the app has moved again, re-capture before trusting a frame.
